# Contributing to FamilyFood

Thanks for your interest in FamilyFood. This guide is written for a first contribution: how to get the project running, what a change should look like, and what is in and out of scope.

FamilyFood is a one-person project maintained in spare time, so a review can take a few days. By taking part you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Getting set up

You need:

- A Mac with Xcode 26 or later. The project is developed with Xcode 27 and CI tests on both; the deployment target is iOS 17.
- An iPhone simulator. If none is installed, add one in Xcode under Settings ▸ Components.
- [XcodeGen](https://github.com/yonaskolb/XcodeGen#installing), for example `brew install xcodegen`.

Fork the repository, then clone your fork and run the tests:

```sh
git clone https://github.com/<your-username>/FamilyFood.git
cd FamilyFood
scripts/test.sh
```

`scripts/test.sh` regenerates the Xcode project and runs the whole test suite on the first available iPhone simulator. It is the one command that verifies a change. Extra arguments are passed on to `xcodebuild`, and `FF_DESTINATION` picks a specific simulator:

```sh
scripts/test.sh -only-testing:FamilyFoodTests/SuggestionEngineTests
FF_DESTINATION='platform=iOS Simulator,name=iPhone 17' scripts/test.sh
```

To run the app in the simulator:

```sh
xcodegen generate
open FamilyFood.xcodeproj
```

Select the `FamilyFood` scheme and an iPhone simulator, then run. The simulator needs no signing setup.

To run on a device, copy `Config/Signing.local.example.xcconfig` to `Config/Signing.local.xcconfig`, set your Apple Developer team id and a bundle id prefix you own, and run `xcodegen generate` again. That file is gitignored. Do not put personal values into `Config/Signing.xcconfig`.

The app works without an API key. Only the import features call the Anthropic API, using a key you enter in the app's Settings tab. The tests never need one.

## The Xcode project is generated

`FamilyFood.xcodeproj` is generated by XcodeGen from `project.yml`. It is gitignored.

- Never edit the `.xcodeproj` by hand and never commit it. Changes made in Xcode's project editor are lost on the next `xcodegen generate`.
- To add a source file, put it under a path that a target's `sources:` in `project.yml` already covers (`FamilyFood/`, `FamilyFoodTests/`, `ShareExtension/`), then regenerate.
- To add a target, change a build setting, add an Info.plist key, or share a file between the app and the share extension, edit `project.yml` and regenerate.

## Code conventions

- **MVVM with feature folders.** Each feature lives in `FamilyFood/Features/<Feature>/` with its own `Views/` and `ViewModels/`. Shared data types are in `FamilyFood/Models/`, business logic in `FamilyFood/Services/`, small helpers in `FamilyFood/Utilities/`.
- **Keep logic out of views.** Rules, calculations, parsing and persistence belong in `Services/` or `Models/`, exposed to the UI through a view model. Views lay out and forward user actions.
- **Design tokens come from `AppTheme` only.** Colours, spacing, corner radii and text roles are defined in `FamilyFood/DesignSystem/AppTheme.swift`. Do not use raw hex colours, system font shortcuts or off-scale spacing values in views. Reuse the shared components in `FamilyFood/DesignSystem/` before building a new one.
- **Match the surrounding style.** Naming, comment density and file layout should look like the code next to your change.
- **No new dependencies without discussing first.** The project has no third-party packages. Open an issue before adding one.
- **UI strings are German for now.** Write user-facing text in German. Code, comments, commit messages and pull requests are in English.

For the bigger picture, read [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) and [docs/DESIGN-SYSTEM.md](docs/DESIGN-SYSTEM.md).

## Tests

- Write the test first for logic in view models, services and models. A bug fix starts with a test that fails because of the bug.
- Tests live in `FamilyFoodTests/`, one file per unit under test, with descriptive names such as `test_effectiveKey_trims_the_entered_key`.
- Tests must not hit the network and must not need an API key. Code that talks to the Anthropic API sits behind the `AnthropicParsing` protocol in `FamilyFood/Services/AnthropicService.swift`; inject a fake in tests.
- `scripts/test.sh` must be green before you open a pull request.

## Branches and pull requests

1. Fork the repository and create a branch from `main`.
2. Keep the pull request small and focused: one change, one reason. Unrelated clean-ups go in a separate pull request.
3. In the description, say what changed and why, and how you tested it.
4. Add screenshots for UI changes (before and after, where that applies).
5. CI runs `scripts/test.sh` and must pass.

## Commit messages

Commits follow a Conventional-Commits-like format:

```
type(scope): short summary of what the change does
```

Types in use are `feat`, `fix`, `refactor`, `chore`, `docs`, `build` and `test`. The scope names the area touched, for example `onboarding`, `meal-plan`, `settings`, `import`, `services` or `design-system`. The summary is lower case, has no trailing full stop, and describes the outcome rather than the activity. Examples:

```
feat(onboarding): whisk mark + Gaegu wordmark on welcome header
fix(tabbar): keep tab bar solid on scroll, not transparent
refactor(services): injectable ImageStorageService directory
build(scripts): add scripts/test.sh as the one-command test runner
```

## Proposing larger changes

For anything bigger than a small fix (a new feature, a new screen, a change to the data model, a new dependency), open an issue first and agree on the approach before writing code. This saves you from building something that cannot be merged.

## What is out of scope

FamilyFood keeps all data on the user's device. Please do not propose:

- a backend or server component,
- cloud sync or user accounts,
- analytics, tracking or third-party crash reporting.

The only network requests the app makes are ones the user triggers: parsing an import through the Anthropic API with their own key, and fetching a recipe page they chose to import, together with its picture.

## Content rules

- Only contribute recipes, images and artwork that you created yourself or that are openly licensed. Say which it is in the pull request, and name the licence and source for anything you did not create.
- Never commit API keys, packaged builds (`.ipa`, `.app`, `.xcarchive`) or personal data. This includes screenshots and test fixtures: check them for names, addresses and keys before attaching them.
- An optional guard rejects commits that contain builds or Anthropic API keys. Enable it once per clone:

  ```sh
  git config core.hooksPath scripts/hooks
  ```

## AI-assisted contributions

Contributions written with the help of an AI assistant are welcome. The same bar applies as for any other change:

- You are responsible for understanding and testing what you submit.
- Say in the pull request that an AI assistant was used.
- Do not paste large generated changes that you cannot explain. If a reviewer asks why a line is there, you should be able to answer.
